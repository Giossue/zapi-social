# Idiomas y traducciones

Cómo está montada la traducción de la interfaz hoy y qué hay que tocar para
añadir un texto o un idioma nuevo. La decisión y el alcance viven en
[`planes/i18n-v2.md`](../planes/i18n-v2.md); esto describe el mecanismo.

## Cómo se elige el idioma

No hay prefijo de idioma en la URL. El servidor lo resuelve en cada petición
desde la cookie `zapi_locale` y cae a `es` cuando falta o no está soportado
(`apps/web/i18n/request.ts`).

La cookie la escribe el cliente en tres momentos, todos vía
`syncLocaleCookie` de `apps/web/i18n/locale-cookie.ts`:

- al iniciar sesión, con el `locale` que devuelve la sesión;
- al sincronizar la sesión mientras se navega;
- al cambiarlo en el perfil del Portal, que además refresca la vista.

Así el render del servidor no necesita llamar a la API para saber el idioma. La
cookie no guarda nada de sesión: solo `es` o `en`.

## Dónde vive el texto

```text
apps/web/messages/es.json   # idioma fuente: aquí se escribe primero
apps/web/messages/en.json   # traduce las mismas claves
apps/web/messages/es.d.json.ts  # generado, no se edita a mano
```

Español es la fuente. `next.config.ts` activa `createMessagesDeclaration`
apuntando a `es.json`, y `apps/web/global.d.ts` usa esa declaración para tipar
`useTranslations`. Consecuencia práctica: **una clave que no exista en
`es.json` falla en `typecheck`**, y también falla pasar un argumento que el
mensaje no declara.

Esa declaración se regenera durante `build` y `dev`, no en `typecheck`. Tras
añadir claves hay que ejecutar `bun run build` antes de `bun run typecheck`, o
el tipado seguirá viendo el catálogo anterior.

## Añadir un texto

1. Añadir la clave a `es.json` **y** a `en.json`, en el espacio de nombres de la
   feature. Los catálogos están ordenados alfabéticamente en todos sus niveles.
2. En el componente, `const t = useTranslations("miFeature")` y usar `t("clave")`.
3. `bun run build` para regenerar la declaración.
4. `bun run typecheck`, `bun run audit:i18n` y `bun run audit:i18n-hardcoded`.

Elegir la clave por lo que significa, no por lo que dice: `deleteWarning`, no
`estaAccionNoSePuedeDeshacer`.

### Valores dentro del texto

Los argumentos van en ICU, nunca concatenados:

```json
{
  "openActions": "Abrir acciones para {name}",
  "trialDaysValue": "{count, plural, one {# día} other {# días}}",
  "referenceLimit": "Puedes usar hasta {max, number} imágenes de referencia."
}
```

```tsx
t("openActions", { name: account.displayName })
t("trialDaysValue", { count: plan.trialDays })
```

Un número que se muestra debe declararse `{n, number}` para que se formatee con
el idioma activo. Un texto que cambia con una cantidad va en `plural`, no en un
ternario: el inglés y el español no parten las cantidades igual.

### Fechas, horas y calendarios

Usar los formatos con nombre en vez de repetir opciones de `Intl`:

```tsx
const format = useFormatter()
format.dateTime(value, "date") // "date" | "dateTime" | "time"
```

Están definidos en `apps/web/i18n/request.ts`. Para `date-fns` y FullCalendar,
que traen sus propios catálogos, usar `useDateLocale()` de
`apps/web/lib/date-locale.ts`.

## Qué no se traduce en el código

- **`packages/ui` no traduce.** Los primitives no conocen el idioma activo ni
  deben depender de `next-intl`. Reciben el texto ya resuelto por props; los
  envoltorios que lo suministran están en `apps/web/components/`.
- **La API no traduce.** Devuelve claves y códigos estables
  (`AUTH_SESSION_EXPIRED`) y la interfaz pone el texto. El único diccionario de
  errores es `useApiErrorMessage` de `apps/web/lib/api-error-message.ts`: un
  código sin texto propio cae al mensaje genérico en vez de mostrarse crudo.
- **Nombres propios y valores técnicos.** Meta, Instagram, PostgreSQL, `KB`.
- **Rótulos accesibles que vienen de shadcn/ui.** Se copian literales por la
  regla source-first; cambiarlos haría divergir los primitives de su fuente en
  cada actualización.

## Correos

Los correos transaccionales no usan `messages/`. Su texto por defecto vive en
`apps/api/src/email/email-template-catalog.ts`, con un juego por idioma, y un
administrador puede sobrescribirlo desde Admin. El idioma sale de
`users.locale` del destinatario, no de quien dispara el envío.

## Auditores

```bash
bun run audit:i18n            # paridad de claves y de argumentos ICU entre idiomas
bun run audit:i18n-hardcoded  # texto de interfaz escrito en el código
```

El primero existe porque el tipado solo cubre el idioma fuente: una clave que
falte en `en.json` no rompe `typecheck`. También comprueba las claves
construidas en ejecución —``t(`status.${row.state}`)``— verificando que su
prefijo exista y sea un grupo.

El segundo cubre el hueco contrario: si una superficie nunca se migró, los dos
catálogos siguen sincronizados y el primero pasa. Prohíbe cualquier literal en
posición de presentación —nodo JSX, prop de rótulo, plantilla con
interpolación, `toast.*`—, sin mirar el idioma ni la longitud. Se comprueba a
sí mismo contra casos conocidos antes de escanear. El detalle de qué descarta
está en [`apps/web/CLAUDE.md`](../../apps/web/CLAUDE.md).

Ninguno de los dos sustituye mirar la pantalla en los dos idiomas.

## Añadir un idioma

El idioma es un valor cerrado del contrato, así que no basta con dejar un JSON
nuevo en `messages/`. Con ruso como ejemplo:

1. `packages/contracts/src/locale.ts`: añadir `"ru"` a `supportedLocaleSchema`.
   De ahí sale el tipo que usan la API, la web y la columna `users.locale`.
2. `apps/web/i18n/locales.ts`: añadir `"ru"` a `supportedLocales`.
3. `apps/web/messages/ru.json`: traducir **todas** las claves de `es.json`.
   `audit:i18n` falla mientras falte una.
4. `apps/web/lib/date-locale.ts`: mapear el catálogo de `date-fns` y el de
   FullCalendar. Sin esto los meses y los encabezados del calendario se quedan
   en el idioma anterior.
5. `apps/api/src/email/email-template-catalog.ts` y `email-chrome.ts`: añadir el
   juego de textos del nuevo idioma. `copy` está tipado como
   `Record<SupportedLocale, …>`, así que el paso 1 deja el compilador señalando
   exactamente lo que falta.
6. `apps/web/features/profile/components/portal-profile-page.tsx`: el selector
   de idioma tiene su propia unión `"" | "es" | "en"` y un `SelectItem` por
   idioma. El nombre visible sale de `common.<idioma>` en los catálogos, así
   que también hay que añadir `common.ru` en todos ellos.
7. `bun run build`, `bun run typecheck`, `bun run audit:i18n` y revisar la
   interfaz en el idioma nuevo.

Un idioma que se escriba de derecha a izquierda necesitaría además decidir el
`dir` del documento y revisar los primitives; hoy no hay ninguno soportado.
