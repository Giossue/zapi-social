Zapi Social

Installation, operation, demo, update, and troubleshooting guide for the self-hosted social publishing platform.

Requirements Installation First setup Demo mode Updates Support Third-party credits

1. Requirements

  • Linux server with a current Docker Engine and Docker Compose v2.
  • Recommended minimum: 4 CPU cores, 8 GB RAM, and 20 GB free disk space.
  • Two HTTPS hosts: one for Web and one for API.
  • Outbound HTTPS access for configured social, billing, email, and media providers.

Shared hosting without Docker is not supported. PostgreSQL and Redis must not be exposed to the public internet.

2. Installation

Extract the purchased archive, enter the application directory, and create the private environment file. 

cp .env.example .env
chmod 600 .env
openssl rand -hex 32
openssl rand -base64 32

Replace every CHANGE_ME value. Generate independent values for PostgreSQL, Redis, JWT, and the provider encryption key. The provider key must be exactly 32 random bytes encoded as canonical Base64. 

WEB_ORIGIN=https://app.example.com
API_PUBLIC_ORIGIN=https://api.example.com
COOKIE_SECURE=true

Validate, build, and start the stack:

docker compose config --quiet
docker compose build --pull
docker compose up -d
docker compose ps
docker compose logs migrate

The expected result is healthy PostgreSQL, Redis, API, Worker, and Web services. The one-shot migrate service must exit successfully.

3. First setup

Open the Web URL. An empty installation redirects to /setup. Create the Platform Admin with a unique email and strong password. The operation is serialized, audited, and can succeed only once.

Sign out after setup and register a different account at /register to create the first Portal workspace. A Platform Admin intentionally has no customer workspace.

Complete these checks before going live:

  1. Configure plans, email, CAPTCHA, billing, languages, and providers in Admin.
  2. Register exact OAuth callback URLs from Admin in each provider.
  3. Test email, billing webhooks, and each enabled provider with non-customer credentials.
  4. Verify /v1/health through the public HTTPS API host.

4. Read-only marketplace demo

Prepare demo accounts while DEMO_MODE=false: complete setup, then register the Portal owner. Seed synthetic data by passing that owner's email only to the one-shot command: 

docker compose run --rm \
  -e DEMO_OWNER_EMAIL=owner@example.com \
  api node apps/api/dist/scripts/seed-demo.js

The command is idempotent. It creates synthetic channels without tokens, historical posts, drafts, board tasks, and notifications. It does not connect to external providers.

Then set DEMO_MODE=true in .env and recreate the public services: 

docker compose up -d --force-recreate api worker web

Safe reads and session operations remain available. Product mutations return HTTP 403 with DEMO_MODE_READONLY, and Web displays a read-only notice.

Never reuse demo passwords or demo data in a customer installation. Keep the demo on an isolated database and rotate its account passwords regularly.

5. Updates and backups

Before every update, verify the current system and create matching PostgreSQL and uploaded-file backups. Store them encrypted outside the server. 

docker compose ps
mkdir -p backups
docker compose exec -T postgres sh -c \
  'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > "backups/database-$(date +%Y%m%d-%H%M%S).sql"
docker compose exec -T api \
  tar -C /app/.data -czf - files \
  > "backups/files-$(date +%Y%m%d-%H%M%S).tar.gz"

Keep .env, backups, and Docker volumes. Replace application files with the new release, compare the new .env.example, then run: 

docker compose config --quiet
docker compose build --pull
docker compose run --rm migrate
docker compose up -d --remove-orphans
docker compose logs --tail=200 migrate api worker web

Do not reverse migrations automatically. If rollback is required, stop the application and restore the matching database and file backups in a maintenance window.

6. Troubleshooting

Problem Check
A service is unhealthy Run docker compose logs --tail=200 postgres redis migrate api worker web. Check secrets, origins, ports, and memory.
Login fails behind HTTPS Confirm exact WEB_ORIGIN and API_PUBLIC_ORIGIN, then use COOKIE_SECURE=true.
OAuth callback is rejected Compare the provider callback character-for-character with the URL shown by Admin.
Uploaded files disappear Confirm API and Worker share the files-data volume. Never delete volumes during a routine restart.

7. Support package

When requesting support, include the application version from RELEASE.txt, browser and server versions, the failing route, reproduction steps, and redacted service logs.

Never send .env, passwords, cookies, JWTs, OAuth tokens, SMTP credentials, provider secrets, customer data, or database backups.
