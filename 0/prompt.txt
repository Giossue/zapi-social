## Por qué hace falta un auditor

El typecheck no ve una columna muerta. Sigue existiendo en el tipo inferido de la tabla, así que
nadie tiene que leerla para que el proyecto compile. Y mirar qué tablas están vacías en la base no
sirve: una columna puede tener datos escritos por una migración o un seed y no leerse nunca desde
el producto.

El auditor parsea el schema con un contador de llaves —no por indentación, así no lo parten los
`sql` multilínea ni los objetos de opciones—, resuelve los `...timestamps`, y busca cada nombre en
sus dos formas, camelCase y snake_case.

Las migraciones (`packages/database/drizzle/`) y los artefactos de build quedan fuera del barrido a
propósito: nombran todas las columnas siempre y convertirían cualquier campo muerto en usado.

## Los tres niveles de certeza

No todos los nombres se pueden buscar con la misma confianza, así que los hallazgos van separados:

| Nivel | Qué significa | Fiabilidad |
| --- | --- | --- |
| `muerta` | Ni el camelCase ni el snake_case aparecen en ningún archivo fuera del schema | Alta, accionable |
| `dudosa` | El nombre solo aparece en archivos que no tocan la tabla | Requiere mirarlo |
| `solo-schema` | Solo se menciona en un índice, constraint o clave foránea del propio schema | Alta |

### Tabla completa

**`authIdentities` / `auth_identities`** — `schema.ts:205`, 11 columnas, cero referencias.

Modela el enlace de identidades OAuth externas a un usuario: `provider`, `providerSubject`,

Esa responsabilidad acabó viviendo en `socialAccountCredentials`. La tabla parece un diseño

decisión explícita: si la rotación de claves está en el plan, falta el lector; si no lo está, la
columna está prometiendo una garantía que el sistema no da.

## Dos límites del método

**`select()` sin lista de columnas trae todas.** Una columna puede viajar en la respuesta HTTP sin
que nadie la lea explícitamente. El auditor la marca muerta y tiene razón funcionalmente, pero el
payload la incluye. Importa si alguna de estas columnas es sensible.

**Muerta en código no es lo mismo que segura de borrar.** Puede haber datos escritos por
migraciones, seeds o procesos externos. El auditor entrega la lista corta a revisar; la decisión de
borrado es un paso aparte y necesita mirar la base.

Un tercer detalle menor: los archivos `messages/*.d.json.ts` de i18n entran en el barrido por su
extensión `.ts`. Eso solo ensancha el conjunto de "archivos que tocan la tabla", lo que hace al
auditor **más conservador** —menos hallazgos, no falsos positivos—, así que se dejó así.

## Reejecutar

```bash
bun run audit:schema                          # todo
bun run audit:schema --level muerta           # solo lo accionable
bun run audit:schema --table socialAccounts   # una tabla (nombre TS o SQL)
bun run audit:schema --fail-on-findings       # para CI
```

   descifrar cada fila.

   su vertical, para que no se confundan con basura en la próxima limpieza.
